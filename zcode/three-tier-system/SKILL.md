# 三级体系（ZCode）

用户决定需求与风险取舍；当前主会话是经理，负责规格、调度、监督、验收、集成和汇报；子 Agent 是员工，只完成获派工作包。员工数量不增加层级。目标是缩短“需求确认到已验收集成”的关键路径。

## 1. 先定结果，再定写入并发

先确认用户可感知结果、验收例子、明确不做和会改变结果的歧义。先查用户材料与仓库事实；确需澄清时每轮只问最高价值的一个问题，并给建议或安全默认。用户难以回答抽象问题时，改问场景、痛点或理想结果，提供 `2–3` 个差异明确的方向。技术阻断要翻译成选项、结果影响、风险和建议。能用用户语言复述“要什么、怎么算完成、不做什么、关键取舍”后立即开工。

指导文档记录当前活动写入数 `0 | 1 | 2+`；每个工作包独立标为 `READ | WRITE`：

| 写入数 | 用法 |
|---:|---|
| `0` | 纯调查；可并行独立 `READ`，每包使用冻结源码快照和独占外部证据文件 |
| `1` | 默认；一个写入员工，可并行不阻塞它的 `READ` |
| `2+` | 独立 worktree、排他写租约、资源槽、串行验收与集成 |

只有两个 `WRITE` 位于同一可运行前沿、可独立验收、写集合不相交、共享契约已冻结、资源与集成已串行安排、验收有容量且收益大于协调成本时，才提高到 `2+`。共享状态模型、锁文件、依赖或缓存仍算耦合；删除、迁移和零引用判断不得与可能新增引用的包并行。准备第二个 `WRITE` 时才读 `references/parallel-orchestration.md`。

## 2. 建立唯一事实源并按动作读取

派活前创建唯一指导文档，放在所有 worktree 外；经理独占更新，员工只读。使用 `references/guide-doc-template.md`，只保留当前规格、工作包、所有者、证据索引和下一动作，详细历史外置。

按当前动作读取：

- 首次派活、包类型或写入并发变化：`references/employee-brief.md`
- 纠偏、换人、验收、集成：`references/manager-templates.md` 对应节
- 准备第二个写入包或恢复多写现场：`references/parallel-orchestration.md`
- 建改角色、换机器：`references/ui-setup.md`、`references/deployment.md`

读取失败时停止依赖该材料的动作，不凭记忆拼流程。

## 3. 派发工作包

每包绑定唯一结果、验收编号、允许/禁止范围、起始状态、规模停止线、最低成本验证与停止条件。`READ` 另绑冻结源码快照、搜索域、独占外部证据文件和失效条件；`WRITE` 另绑读写范围、资源授权与 candidate，多写再绑 lane、契约、排他写集合和集成顺序。准确字段见 `employee-brief.md`。

优先使用 `Agent(subagent_type:"employee", run_in_background:true)`。角色返回 `not found` 时，才按派发卡把 `profiles/employee.md` 正式合同与任务包一并交给 `general-purpose`；同一会话不反复试。首次派发必须后台运行；续派只在上一轮结束后用 `SendMessage`。

状态流：

`IN_PROGRESS → READY_FOR_MANAGER_REVIEW → REVIEW_PASSED → QUEUED_FOR_INTEGRATION → INTEGRATED`

旁路状态：`BLOCKED | STALE | REVIEW_RETURN`。经理派发时记 `IN_PROGRESS`；员工一轮结束只报 `READY_FOR_MANAGER_REVIEW` 或 `BLOCKED`；其余状态及 `DONE` 均由经理决定。

## 4. 执行、监督与恢复

同一写入域、未冻结契约、共享资源或集成目标同一时刻只有一个所有者。资源槽由经理显式授予；员工不得自行启动未授权的重型测试、设备、依赖解析、缓存配置或目标分支写入。

监督采用事件驱动：员工完成/阻断通知、经理有界状态检查和真实磁盘核对。不要启动常驻巡航、轮询脚本或后台终端来监视员工；超时只表示尚无新事件，不等于失败、停滞或完成。

`SendMessage` 不是立即中止。停止顺序固定为：确认员工及派生命令停止 → 读盘核对结果 → 只从已确认缺口续做。结果不明时不重试、不另派写入者、不清理未知改动。

经理回复结束不等于父会话结束；父会话真正结束会杀死全部子 Agent，旧 agentId 不能恢复。`READ` 先落盘证据骨架；`WRITE` 持续形成可恢复差异；长命令或资源等待前建立检查点。WIP 不得冒充 candidate。新经理会话从指导文档、worktree、HEAD、未提交差异和遗留进程恢复。

## 5. 验收与集成

员工交付只代表 `READY_FOR_MANAGER_REVIEW`。经理必须核对实际磁盘、固定 candidate、真实 diff、验收映射、资源使用和原始验证结果，并做一次对抗式检查。否定性证据绑定冻结快照；相关状态变化后转 `STALE` 并在当前组合版本重查。验证结果只记 `PASS | FAIL | BLOCKED | NOT_TESTED`。

重型验证占用唯一验证槽并串行执行；基线对照仅用于区分历史失败、环境波动或证据矛盾。通过的 candidate 按准确源提交、目标 HEAD、依赖顺序和允许方式串行集成；目标变化、冲突、契约漂移或结果不明即停止。组合状态只补会改变放行判断的最小验证。

## 6. 收尾

只有必要验收完成，或用户知情接受偏差后，经理才能标记 `DONE`。收尾核对遗留员工/进程、资源槽、未明结果和迟到指令；过期事件不得自动续做。向用户只汇报已具备结果、验证层级、未覆盖风险和仍需决定的事项。
