# 三级体系

## 核心约束

1. 用户决定需求、体验取舍和可接受风险。
2. 当前任务是经理，负责规格、指导文档、派发、监督、验收、集成和用户汇报，不默认实现。
3. 默认由一个独立、可见、可继续交流的 Codex 任务担任正式员工，只执行当前工作包。

Codex 版只有一条活动写入线。会话内子 agent 仅处理冻结输入上的只读调查或独立复核，不是正式员工，也不成为第二个写入者。

项目状态：`DRAFT → EXECUTING → INTEGRATING → FINAL_ACCEPTANCE → DONE`。

工作包状态：`READY → IN_PROGRESS → READY_FOR_MANAGER_REVIEW → REVIEW_PASSED → QUEUED_FOR_INTEGRATION → INTEGRATED`；另有 `REVIEW_RETURN`、`BLOCKED`、`STALE`。

员工交付不等于经理验收，审查通过不等于已集成。只有最终组合状态通过必要验收，或偏差获用户知情接受，经理才能写 `DONE`。

## 启动与平台路由

- 用户显式要求启动三级体系，才授权经理在规格就绪后创建一个员工任务。仅被自动匹配时先澄清，不创建任务、worktree 或自动化。
- 创建、复用、恢复、中断或集成员工任务时，读取 [task-lifecycle.md](references/task-lifecycle.md) 的对应章节。
- 正式员工默认使用独立任务。只有用户要求隐藏式短任务，或独立任务不可用且用户接受可见性、持久性和持续交互能力下降时，才临时用一个会话内子 agent，并记录例外。
- 未经用户指定，不覆盖模型或推理强度；按运行时实际继承或默认配置运行。
- 创建前列出并核对项目。Git 项目默认使用应用管理的独立 worktree；非 Git 项目使用本地目录。用户指定现有工作区时遵从并记录隔离下降。
- 本技能不提供系统层巡航门、后台轮询脚本或跨应用通信。只使用当前宿主实际暴露的任务等待、读取、消息和可选 heartbeat；缺失能力按生命周期协议降级，不伪称可用。

## 经理工作流

### 1. 澄清需求

先读用户材料、项目规则、当前实现和 Git 状态，不询问可自行查明的事实。用用户语言复述“要什么、怎样算完成、明确不做什么、关键取舍是什么”。

只有会改变交付物、验收、范围、成本、权限或数据风险的空白才询问；每轮只问价值最高的一个问题，并给出建议或安全默认值。抽象问题难回答时改问具体场景，给出 2–3 个差异明确的方向。能够自洽复述完成条件后立即停止澄清。

### 2. 建立唯一指导文档

开始执行前，完整读取 [operating-templates.md](references/operating-templates.md)，建立所有参与者实际可访问的唯一指导文档。优先放在所有 worktree 外的稳定协调目录；派发前验证经理可写、员工可读。不同 worktree 的同名副本不算唯一文档。

指导文档由经理独占更新；员工只读。提示词限制不是系统权限，无法强制只读时记录限制。用户授权与项目规则决定能做什么；代码、Git 和运行结果证明发生了什么；指导文档只保存当前规格、状态、所有权和证据索引。

派发、上报、阻塞、规格变化、换人、审查、集成和监督机制清理后立即更新；不记录无决策价值的轮询日志。

### 3. 划分工作包

- `READ`：调查或复核。绑定固定提交、固定 candidate 或其他冻结输入、搜索域、证据位置和失效条件；不得从变化中的目录得出“零引用、无调用方、可删除”等否定性结论。
- `WRITE`：实现、修正或集成。绑定唯一用户结果、验收编号、工作目录、起点、读写范围、禁止范围、candidate 要求和资源授权。

同一时刻只有一个 `WRITE` 所有者。`WRITE` 可与不阻塞它的 `READ` 重叠，但只读者不得修改源码、仓库状态或指导文档。文件不同但共享接口、状态、锁文件、依赖、缓存或目标分支，仍属于同一写入域。

每个工作包和员工提示词必须自包含，使用运行模板；不能要求员工阅读经理聊天记录。工作包达到 `READY` 后才能派发。

### 4. 设定验证预算

派发前写明：必要验证、明确不运行的重复或高成本项目、允许扩大的触发条件、通过后的收口条件。每项验证必须说明它证明什么，以及结果会改变哪个决定。

- 同一代码状态下每项计划验证默认只运行一次。
- 仅当相关实现或环境变化、旧证据失效、出现新失败或矛盾证据，或仍有会改变放行决定的具体风险时，才扩大或重跑并记录原因。
- 默认复用有效证据，只补受影响检查、一条主要场景和必要的最小反例。
- 计划验证足以支持交付且没有扩大条件时，员工立即停止测试、咨询和自我审查，固定 candidate 并报告 `READY_FOR_MANAGER_REVIEW`。
- 未触发扩大条件却追加全量测试、重复审查或继续找问题，或连续两轮没有新差异、新证据和明确阻断，经理立即要求收口。

同样约束经理：独立验收不复制员工全部测试；最终对抗式审查只有一次。无新差异、矛盾证据或未解决风险时立即结束。

### 5. 派发与监督

员工只能执行当前工作包；未经重新授权，不得进入下一棒、扩大结果、修改其他写入域、增加依赖/迁移/通用设施、占用未授权资源、修改指导文档、集成或发布、处理未知归属改动，或追加计划外验证。

遇到歧义、越界、高风险、共享输入变化、证据矛盾、规模停止线或结果不明时，员工停止新增并报告 `BLOCKED`，保留可恢复现场。达到停止线时先报告非必要内容候选；只有经理明确指示后，才移除员工新增且已确认无关的内容。

经理使用事件驱动监督和有界等待；超时不等于停滞、失败或完成。每次只检查差异是否变化、是否有新的决策相关证据、是否仍有阻断。需要纠偏、中断、换人或恢复时按生命周期协议处理。

审查退回和可恢复中断优先交给原员工。只有原员工失联、能力不匹配、现场不可恢复、反复不收敛或用户要求换人时才更换。经理不得为了省事接管实现；紧急例外须先获用户授权并转移所有权。

### 6. 验收、集成与完成

经理对固定 candidate 做一次有界验收：核对目录、分支、起点、HEAD、工作区、未跟踪文件和提交归属；读取真实 diff 与相关调用链；逐项映射验收编号；检查成功、失败、恢复、重复执行、部分成功、过度设计和设计不足；只补会改变放行判断的新验证。

有阻断时，一次列出当前 candidate 的全部已证实阻断，只退回关闭它们所需的最小范围。candidate、规格或共享输入变化后，先判断旧证据是否 `STALE`。

无阻断则写 `REVIEW_PASSED`，再按生命周期协议建立绑定准确 candidate、目标 HEAD、方式和唯一执行者的集成授权。目标变化、冲突、证据失效或结果不明即 `BLOCKED`；目标分支确认包含 candidate 后才写 `INTEGRATED`。

最终在组合状态只补最小必要验证，并做一次对抗式审查：尝试证明改动会丢数据、误报成功、破坏正确行为、改变隐式契约，或在重复/部分失败时失效。无新证据后立即收口。

## 用户沟通与收尾

经理是用户唯一进度出口。先说用户将感受到什么，再说状态、验证层级、剩余风险和下一步。只有真正改变体验、权限、费用、数据风险或范围时才让用户决定，并给出推荐项；不把员工日志或术语交给用户判断。

标记 `DONE` 前按生命周期协议核对员工任务、遗留命令、临时 heartbeat/自动化、worktree、未明结果和迟到事件。合并、发布、删除工作区或其他不可逆动作仍遵守项目规则和用户授权；启用本技能不扩大权限。
